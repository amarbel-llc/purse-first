# Local MCP Plugin Development & Testing

**Status:** Proposal
**Authors:** friedenberg

## Problem

When developing an MCP server that is also a purse-first plugin (e.g. lux,
grit, chix), you need to test your local changes against a real Claude Code
session. The marketplace version of your plugin is loaded by default, but it
points to a cached or released build — not your working tree.

There is no built-in way to swap the marketplace version for a local dev build
and exercise the tools interactively within Claude Code.

## Current Manual Workflow

The following steps were validated using lux as a test case.

### 1. Build the local MCP server

From the plugin's repo root:

```sh
nix build
```

This produces a store path like
`/nix/store/<hash>-<name>-<version>/bin/<binary>`.

### 2. Create a project-scoped `.mcp.json`

Add a `.mcp.json` to the repo root that defines a dev-named MCP server
pointing to the nix store path from the build:

```json
{
  "mcpServers": {
    "<name>-dev": {
      "type": "stdio",
      "command": "/nix/store/<hash>-<name>-<version>/bin/<binary>",
      "args": ["mcp", "stdio"]
    }
  }
}
```

The `-dev` suffix avoids a naming conflict with the marketplace version of the
same plugin. Both can coexist in the same session.

### 3. Restart Claude Code

Claude Code reads `.mcp.json` at session startup. Restart to pick up the new
server. The dev build appears as tools prefixed with `mcp__<name>-dev__*`
alongside the marketplace `mcp__plugin_<registry>_<name>__*` tools.

### 4. Exercise the tools

Use the dev tools directly in conversation to verify behavior against the
local codebase. For example, with lux-dev:

```
mcp__lux-dev__diagnostics  → run diagnostics on project files
mcp__lux-dev__hover        → get type info at a position
mcp__lux-dev__references   → find all usages of a symbol
```

### 5. Iterate

After making code changes:

1. Rebuild: `nix build`
2. Update the store path in `.mcp.json`
3. Restart Claude Code

## Pain Points

- **Manual store path management.** Each rebuild produces a new store path.
  The `.mcp.json` must be updated to match.
- **Restart required.** Claude Code does not hot-reload MCP servers.
- **No automation.** The build → update → restart cycle is entirely manual.
- **`.mcp.json` uses absolute nix store paths.** The `./result` symlink would
  be more stable but may not resolve correctly depending on how Claude Code
  spawns the MCP subprocess.

## Proposed: `just dev-mcp`

A justfile target that automates the build and `.mcp.json` generation:

```just
# Generate .mcp.json pointing to the current nix build for local dev testing
dev-mcp:
    #!/usr/bin/env bash
    set -euo pipefail
    store_path=$(nix build --print-out-paths)
    binary=$(basename $(ls "$store_path/bin/" | head -1))
    cat > .mcp.json <<EOF
    {
      "mcpServers": {
        "${binary}-dev": {
          "type": "stdio",
          "command": "${store_path}/bin/${binary}",
          "args": ["mcp", "stdio"]
        }
      }
    }
    EOF
    echo "Wrote .mcp.json → ${store_path}/bin/${binary}"
    echo "Restart Claude Code to load ${binary}-dev"
```

This could be:

1. Added to each plugin's justfile as a convention.
2. Provided as a shared script in purse-first that plugins source.
3. Generated by `purse-first` itself as a subcommand
   (e.g. `purse-first dev-mcp --flake .`).

## Proposed: `purse-first dev-mcp`

A purse-first subcommand that any plugin can use:

```sh
# From any plugin repo with a flake.nix
purse-first dev-mcp

# Or with explicit flake ref
purse-first dev-mcp --flake .#my-package
```

Behavior:

1. Run `nix build` (or use `--flake` ref).
2. Discover the binary name from the store path's `bin/` directory.
3. Discover the MCP server args from the plugin's `plugin.json`
   (in `share/purse-first/<name>/plugin.json`).
4. Write `.mcp.json` to the current directory with a `-dev` suffixed name.
5. Print instructions to restart Claude Code.

This keeps the dev flow consistent across all purse-first plugins without
each one needing to implement it independently.

## Considerations

- `.mcp.json` should be in each plugin's `.gitignore` since it contains
  machine-specific nix store paths.
- The `-dev` naming convention allows side-by-side comparison between
  marketplace and dev versions of the same plugin.
- Skills bundled with the plugin are not loaded via `.mcp.json` — only the
  MCP server. Skill testing requires a separate mechanism (or marketplace
  reinstall).
- The `./result` symlink could be used instead of absolute store paths if
  Claude Code resolves symlinks when spawning MCP subprocesses. This would
  eliminate the need to update `.mcp.json` on every rebuild.
